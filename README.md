# Навчальний Пульс

Веб-версія застосунку Стрийського фахового коледжу ЛНУП: розклад, журнал, новини, контакти та реквізити оплати. Працює на телефоні, планшеті й комп'ютері, встановлюється на домашній екран як PWA. Хостинг — безкоштовний Cloudflare Workers.

**Розгорнута версія:** <https://edupulse-pwa.olehnana1236.workers.dev>

## Можливості

- **Розклад** — вибір групи або викладача, календар із доступними датами, кнопка «Сьогодні», пари з аудиторіями, позначка замін, підсвітка пари, яка триває зараз, і прогрес вивчення предметів.
- **Журнал** — оцінки, теми уроків, домашні завдання, самостійна робота та середній бал по предметах. Тепер відкривається **через вхід акаунтом Google** (той самий шлях, що й в офіційному застосунку коледжу).
- **Журнал для батьків** — окрема вкладка `#/parent`: батько сканує QR, який студент показує у своєму застосунку коледжу, і бачить той самий журнал. Входу Google тут не треба, тому працює на будь-якому телефоні, включно з iPhone, і на будь-якому домені.
- **Сповіщення про нові оцінки** — вмикається одним дотиком у вкладці «Журнал» або «Журнал для батьків»: браузер надсилає push, коли в журналі з'явиться нова оцінка. Перевірка журналу — двічі на годину.
- **Новини** коледжу — з сайту на WordPress.
- **Контакти** адміністрації, навчальної частини, завідувачів і бухгалтерії.
- **Реквізити оплати** з автопідстановкою прізвища, імені та групи у призначенні платежу.
- **Темна й світла тема**, офлайн-кеш, встановлення на домашній екран.

Розклад, новини, контакти й реквізити доступні без входу. Журнал коледж закрив для публічного доступу, тому для нього потрібен вхід — тим самим способом, яким заходять у офіційний застосунок коледжу. Батькам достатньо QR від студента: окремого акаунта в них не вимагаємо.

## Як запустити локально

```bash
npm install
npx wrangler dev
```

Відкрити <http://localhost:8799>

Локально вхід працює саме через `localhost`: Firebase звіряє hostname сторінки з переліком «Authorized domains» і `127.0.0.1` він не вважає за `localhost`.

Щоб працювали й сповіщення, скопіюйте `.dev.vars.example` у `.dev.vars` і впишіть туди `VAPID_PRIVATE_KEY` (ключ генерується командою `npm run vapid:gen`).

## Як задеплоїти

```bash
npx wrangler login
npx wrangler deploy
```

Wrangler покаже адресу виду `https://edupulse-pwa.<твій-нік>.workers.dev`.

## Вхід у журнал

Коледж припинив публічний журнальний API: старий ендпоїнт `journal-api.sclnau.com.ua` відповідає `410 Gone` на будь-який запит. Замість нього коледж підняв власний кабінет — `tt-api.sclnau.com.ua` («EduPulse Parent Mode API»), який віддає журнал лише за токеном користувача.

Тому застосунок входить так само, як офіційний застосунок коледжу — через той самий Firebase-проєкт `edupulse-main`:

1. браузер відкриває popup Firebase-обробника на домені проєкту (`edupulse-main.firebaseapp.com`);
2. користувач входить в акаунт Google;
3. обробник отримує код від Google, а Firebase SDK сам міняє його на id-токен проєкту (`aud` = `edupulse-main`) і refresh-токен — застосунок бере їх із увійденого користувача;
4. воркер перевіряє токен через `accounts:lookup` — справжність і походження з проєкту коледжу;
5. далі журнал читається через `GET /journal/me` з `Authorization: Bearer <токен>`.

Хто саме бачить журнал, вирішує сам кабінет коледжу: він знає свої акаунти й може заблокувати будь-який (`exists`, `active`, `suspended`). Тому застосунок не фільтрує пошту за доменом — інакше до батьків з особистими акаунтами та студентів із закордонних доменів журнал не доходив би.

Firebase-проєкт дозволяє вхід лише з доменів зі свого переліку «Authorized domains», і цей перелік живе в консолі проєкту — змінити його може лише адміністратор коледжу. Тому застосунок спершу питає воркер, чи дозволено наш домен (воркер читає той самий перелік із `/v1/projects`), і якщо ні — одразу каже, що саме треба додати, замість хвилин очікування й «вхід скасовано».

Щоб вхід запрацював на `edupulse-pwa.olehnana1236.workers.dev`, у проєкті `edupulse-main` треба додати цей домен: **Authentication → Settings → Authorized domains**. Після цього код працює без жодних змін — і сам Firebase починає віддавати подію входу нашій сторінці. Локально (`localhost`) вхід дозволений уже зараз: цей домен у переліку є.

Обробник Firebase бере `redirectUrl` за «домен застосунку» і передає його Google як `context_uri`, а Google звіряє `context_uri` з авторизованими JS-origin цього клієнта — у клієнті коледжу там є **лише** `edupulse-main.firebaseapp.com`. Тому в popup лишається саме цей домен: `edupulse-main.web.app` у переліку авторизованих доменів проєкту є, але в авторизованих origin Google — ні, і з ним Google відповідає «Помилка 400: origin_mismatch».

Це той самий проєкт, що й в офіційному застосунку, тож жодних чужих ключів не потрібно.

Вхід відкриває окно Google. Якщо браузер блокує спливаючі вікна, застосунок скаже про це — дозвольте їх для цього сайту й спробуйте ще раз.

Сесія живе година, далі воркер оновлює її через `accounts:refresh`, тож читати журнал треба лише раз на вхід у застосунок.

Клієнтський ID Google, web-ключ Firebase та ID проєкту лежать у відкритому коді — це **публічні ідентифікатори**: ті самі, що вбудовані в офіційний застосунок коледжу, їх видно в будь-якому його завантаженому файлі. Тайна тут потрібна лише одна — приватний ключ VAPID для сповіщень, він лежить у секреті воркера.

## Журнал для батьків (QR)

Офіційний застосунок коледжу — лише на Android, а вхід у журнал через Google до того ж вимагає домену зі списку «Authorized domains». Батьківський шлях коледж зробив сам і він від цього не залежить:

1. студент у застосунку коледжу генерує QR (`POST /parent/qr/create` — під його власним токеном);
2. батько відкриває `#/parent`, наводить камеру на QR або вставляє код із нього текстом;
3. воркер активує код через `POST /parent/qr/activate` — цей ендпоінт у кабінеті коледжу **публічний**, входу не потребує;
4. у відповіді — `parent_access_token`, з яким читається `GET /parent/journal`;
5. «Відв'язати» викликає `POST /parent/token/revoke` і прибирає доступ із пристрою.

Сповіщення в батьківському режимі працюють так само: підписка зберігається з `parentToken` замість refresh-токена Google, а хронологія для таких записів тягне батьківський журнал. Коли строк доступу минає, запис підписки видаляється з KV, щоб не перевіряти те, чого вже немає.

Код з QR — це і є згода студента. Він не потрапляє в URL (туди, де його бачать історія та чужі закладинки), не виводиться в консоль і не пишеться в логи: застосунок передає його лише в тілі `POST /api/parent/activate` і відразу очищає поле.

## Сповіщення про нові оцінки

Web push працює «на себе»: ключі VAPID наші власні, push-сервіс стандартний (Chrome/Firefox надсилають до нього згенеровані ними ключі), а журнал перевіряє власний воркер за розкладом.

1. **Простір KV** для підписок (уже створений і прописаний у `wrangler.toml`):

   ```bash
   npx wrangler kv namespace create PUSH_SUBS
   ```

   Після створення вставте отриманий `id` у секцію `[[kv_namespaces]]` файлу `wrangler.toml`.

2. **Ключі VAPID** — згенерувати пару:

   ```bash
   npm run vapid:gen
   ```

   Публічний ключ (`BD9WRsrp…`) лежить у `worker.js` і роздається браузерам, це нормально. Приватний — у секрет воркера:

   ```bash
   npx wrangler secret put VAPID_PRIVATE_KEY
   ```

   Для локального запуску покладіть його ж у `.dev.vars` (див. `.dev.vars.example`).

3. **Хронологія** — `crons = ["23,53 * * * *"]` у `wrangler.toml`, тобто перевірка журналу двічі на годину. На безкоштовному плані Cloudflare хронологія не гарантує точну хвилину.

Як це влаштовано:

- браузер надсилає `POST /api/push/subscribe` з підпискою (endpoint + ключі `p256dh`/`auth`) і своїм refresh-токеном сесії;
- воркер зберігає підписку й **знімок** оцінок у KV, а в `/api/push/key` віддає публічний ключ VAPID;
- щоразу за хронологією воркер оновлює сесію, тягне журнал, порівнює зі знімком і надсилає push лише тим, у кого з'явилась нова оцінка;
- сам push шифрується за RFC 8291 (`aes128gcm`) і підписується за RFC 8292 (VAPID), ключі ніколи не залишають воркер у відкритому вигляді.

Запис у KV робиться лише тоді, коли знімок справді змінився — добова квота записів (1000 на безкоштовному тарифі) не витрачається на порожні перевірки. Якщо сервер журналу раптом віддає обрізану відповідь, такий цикл ігнорується, щоб не прийшли фальшиві сповіщення.

Перевірити локально:

```bash
npm test            # шифрування за тест-вектором RFC 8291
npm run test:e2e    # наскрізна перевірка: підписка → хронологія → push → розшифрування
```

## Як це працює

```
Браузер ──► Cloudflare Worker (ваш origin)
                ├──► tt.sclnau.com.ua      розклад, групи, контакти, реквізити (публічні)
                ├──► tt-api.sclnau.com.ua  кабінет коледжу: журнал за токеном, журнал і QR для батьків, налаштування входу
                ├──► identitytoolkit.googleapis.com  сесія Firebase коледжу
                ├──► sclnau.com.ua/wp-json     новини (WordPress REST)
                └──► KV                     підписки на push і знімки оцінок

Хронологія (двічі на годину) ──► журнал ──► порівняння зі знімком ──► push-сервіс (FCM/Mozilla)
```

Розклад, новини, контакти й реквізити воркер лише проксіює з публічних ендпоінтів коледжу. Журнал і вхід — лише за токеном самого користувача; POST-запити, які змінюють підписки на сповіщення, перевіряють `Origin`.

## Безпека

- `POST /api/push/subscribe`, `POST /api/push/unsubscribe`, `POST /api/auth`, `POST /api/refresh`, `POST /api/parent/activate` і `POST /api/parent/revoke` перевіряють `Origin` запиту — запити з чужих доменів відхиляються.
- Приватний ключ VAPID лежить у секреті воркера (`wrangler secret`), а не в репозиторії; публічний ключ роздається браузерам — це задумано.
- Google-ключ, клієнтський ID та ID Firebase-проєкту в коді — це публічні ідентифікатори Firebase-проєкту коледжу (як у його офіційному застосунку), а не секрет.
- Воркер перевіряє токен через сам Firebase (`accounts:lookup`), тож чужий або підроблений токен не приймається.
- Воркер віддає журнал лише за токеном, який справді випустив Firebase-проєкт коледжу, і тільки тому, хто за ним стоїть, чужих сесій не зберігає.
- Журналу за поштою чи за ID студента в застосунку немає — і не буде: це був би доступ до чужих оцінок за одним лише відомим рядком тексту. Батьківський доступ існує лише через QR, який свідомо показав студент.
- Батьківський токен лежить у `localStorage` пристрою (так само, як і сесія студента). Спільний телефон — спільний журнал; «Відв'язати» прибирає його з пристрою та відкликає доступ у кабінеті коледжу.

## Відомі обмеження

- **Сповіщення на iPhone** працюють лише у встановленому застосунку (PWA), а не у вкладці Safari: додайте сайт на головний екран і відкривайте звідти.
- Push-сповіщення приходять не миттєво: журнал перевіряється двічі на годину.
- Список доступних дат береться з сервера коледжу, тому в кеші він живе до 15 хвилин.
- Сервер кабінету коледжу час від часу лежить (525) — тоді застосунок показує останній збережений журнал.
- Журнал тепер видно лише студенту коледжу, який увійшов своїм акаунтом, або батькові з QR, який показав студент.
- Вхід на розгорнутому домені потребує, щоб коледж додав `edupulse-pwa.olehnana1236.workers.dev` до «Authorized domains» свого Firebase-проєкту; без цього застосунок одразу пояснює, що саме треба додати. Батьківському входу за QR це не заважає — той працює на цьому домені вже зараз.
- Що саме коледж кладе в QR (голий токен, JSON чи посилання) і скільки живе батьківський доступ — перевірено лише на самому застосунку коледжу, бо тестового QR не існує. Застосунок розбирає всі три форми, а помилку «коду такого немає» пояснює українською. Реальний журнал батьків ще не відкривався.
- Сканування камерою потребує https або `localhost` (так влаштований доступ до камери в браузерах) і працює у Chrome/Android нативно; для iOS Safari підвантажується розпізнавач jsQR. Якщо камера не дозволила — можна вставити код текстом.

## Файли

| Файл | Призначення |
|---|---|
| `worker.js` | API-проксі, вхід через Google, активація батьківського QR, роздача статики, версійний хеш, хронологія сповіщень |
| `webpush.mjs` | шифрування push (RFC 8291) та підпис VAPID (RFC 8292) |
| `auth-domains.mjs` | перевірка домену застосунку за переліком «Authorized domains» Firebase-проєкту |
| `index.html` | каркас застосунку |
| `styles.css` | теми та компоненти |
| `app.js` | логіка екранів: розклад, журнал, журнал для батьків (QR + камера), новини, контакти, оплата, сповіщення |
| `sw.js` | service worker: офлайн-кеш і показ сповіщень |
| `manifest.webmanifest` | маніфест для встановлення PWA |
| `icon-192.png`, `icon-512.png`, `apple-touch-icon.png` | іконки застосунку |
| `scripts/gen-vapid-keys.mjs` | генератор пари ключів VAPID |
| `test/webpush.test.mjs` | тест-вектор RFC 8291 (побайтове порівняння) |
| `test/auth-domains.test.mjs` | перевірка домену за переліком авторизованих доменів Firebase |
| `test/qr-token.test.mjs` | розбирання кода з QR: голий токен, JSON, посилання з параметром або в шляху |
| `test/push.e2e.mjs` | наскрізна перевірка сповіщень на локальному воркері — і студентського, і батьківського |

Версія для кешування рахується як хеш вмісту файлів і підставляється в `index.html` та `sw.js` під час деплою, тому браузер оновлює застосунок сам, без ручного `?v=N`.
